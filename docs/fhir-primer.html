FHIR — Complete Beginner's Guide

What it is, why it matters, what we're building, and how AI fits in. No prior healthcare IT knowledge assumed.

What is FHIR?

FHIR stands for Fast Healthcare Interoperability Resources. It is a standard — a shared language — that healthcare software systems use to talk to each other.

It is published by HL7 International, a non-profit organisation that has been defining healthcare data standards since 1987. The current version is FHIR R4 (R4 = Release 4), which became the dominant standard around 2019 and is now mandated by law in the United States for any software touching Medicare/Medicaid data.

Imagine ten different hospitals each keep patient records in their own format — one uses Excel, one uses a PDF printout, one uses a custom database only they understand. When a patient moves between hospitals, a nurse has to manually re-type the same information. FHIR is the agreement that says: "everyone will describe a patient using the same JSON structure, so any system can read any other system's data without translation."

Why does it exist?

Before FHIR, healthcare IT was a silo. A hospital's radiology system could not talk to its pharmacy system. A patient's GP in London could not electronically receive discharge notes from a hospital in Manchester. Electronic Health Records (EHRs) from different vendors — Epic, Cerner, Meditech — stored data in completely incompatible formats.

The consequences were real and serious:

  • Patients were asked to repeat their medical history at every appointment.
  • Doctors made prescribing errors because they couldn't see what another doctor had already prescribed.
  • Researchers couldn't aggregate data across hospitals for clinical studies.
  • Insurance companies couldn't verify claims without manual paperwork.
The core promise of FHIR
Any FHIR-compliant system can send data to, and receive data from, any other FHIR-compliant system — regardless of vendor, language, or database — because they all agree on the format.

The US government made this concrete in 2020: the 21st Century Cures Act now legally requires hospitals and EHR vendors receiving federal funding to expose FHIR R4 APIs. This is why FHIR expertise is now one of the most in-demand skills in healthcare software.

The USB Analogy

Before USB existed, every device — keyboards, mice, printers, cameras — had its own proprietary plug. You needed a different port on your computer for each device. USB said: "every device will use this one standard connector." Now any USB device plugs into any USB port, from any manufacturer.

FHIR is USB for healthcare data. It defines the "plug shape" (JSON format) and the "electrical signal" (HTTP REST API). Any FHIR system can plug into any other FHIR system.

Just like USB has versions (USB 2, USB 3, USB-C), FHIR has versions (DSTU2, STU3, R4, R5). R4 is the one that matters right now — it's what regulators require and what every major EHR vendor has implemented.

Resources — the building blocks

Everything in FHIR is a Resource. A resource is simply a JSON object that represents one piece of healthcare information. Each resource has a resourceType field that says what it is.

🧑

Patient

Demographics: name, date of birth, gender, address, phone. Maps to our internal Patient table.

🏥

Encounter

A visit, admission, or care episode. Maps to our internal Case (a case IS an encounter in FHIR terms).

📅

Appointment

A scheduled meeting between a patient and a provider. Maps to our Appointment table directly.

✅

Task

A unit of work to be done. Maps to our CaseTask table — e.g. "Schedule follow-up call."

📄

DocumentReference

Metadata about a clinical document (referral, lab result). Maps to our Document table.

📦

Bundle

A container that holds multiple resources together — like a zip file for FHIR data.

Show example: What a FHIR Patient resource looks like in JSON 
{
  "resourceType": "Patient",
  "id": "MRN-2026-00001",
  "identifier": [{
    "system": "https://hcms.example.com/mrn",
    "value": "MRN-2026-00001"
  }],
  "name": [{
    "family": "Smith",
    "given": ["Jane", "Marie"]
  }],
  "birthDate": "1985-03-22",
  "gender": "female",
  "telecom": [
    { "system": "phone", "value": "+1-555-0100" },
    { "system": "email", "value": "jane.smith@email.com" }
  ],
  "address": [{
    "line": ["123 Maple Street"],
    "city": "Springfield",
    "state": "IL",
    "postalCode": "62701"
  }]
}

This is exactly the JSON our FhirController will return when someone calls GET /fhir/R4/Patient/MRN-2026-00001. We build this on-the-fly from our SQL Patients table — no separate FHIR database needed.

Bundles — packaging resources together

A Bundle is a FHIR resource that holds a list of other resources. Think of it as an envelope containing multiple documents. There are two bundle types we use:

Bundle TypeWhen usedOur use
searchsetResponse to a search query — "give me all patients named Smith"GET /fhir/R4/Patient?name=Smith
collectionA group of related resources packaged togetherGET /fhir/R4/Patient/{id}/$everything
A searchset Bundle is like Google search results — a list of matching items. A collection Bundle is like a patient's paper file folder — everything about one person, all together in one place.

Operations & Search

FHIR uses standard HTTP verbs (GET, POST, PUT, DELETE) but adds some special conventions:

PatternExampleMeaning
ReadGET /Patient/123Get one specific patient by ID
SearchGET /Patient?name=SmithFind patients matching criteria
CreatePOST /PatientSubmit a new patient resource
OperationGET /Patient/123/$everythingNamed operation on a resource ($ prefix)

The $everything operation is special — it's a FHIR standard named operation that says "give me everything related to this patient." A system receiving this call must return a Bundle containing the patient plus all their linked resources.

CapabilityStatement — the menu card

When you walk into a restaurant, the first thing you ask for is a menu. It tells you what they serve, what the prices are, and what's available today. FHIR's CapabilityStatement (returned at GET /fhir/R4/metadata) is the menu card for a FHIR server — it lists every resource type it supports, every search parameter, and every operation.

Any FHIR client application — another hospital's EHR, a mobile health app, a research tool — will first call /metadata to discover what your server can do. This is how interoperability is achieved programmatically. Our server will declare support for Patient, Encounter, Appointment, Task, and DocumentReference.

Phase 5 — What we're building

Right now, HCMS is a closed system. Only our own Angular front-end can read and write patient data. Phase 5 opens a FHIR "window" on the side of our system so that any FHIR-compliant external system can:

  • Query our patient records in standard FHIR format
  • Import a new patient from an external EHR (Epic, Cerner) by posting FHIR JSON
  • Download a complete patient record as a portable FHIR Bundle
Key design decision
We do not create a separate FHIR database. Everything lives in our existing SQL Server tables (Patients, Cases, Appointments, etc.). The FhirMappingService translates between our internal format and FHIR JSON on every request. This keeps the system simple and avoids data duplication.

API Endpoints we're building

BASE PATH: /fhir/R4/ — All endpoints require JWT auth
GET/metadataReturns the CapabilityStatement (the "menu card" of what we support)
GET/PatientSearch patients: ?name= ?birthdate= ?identifier= → returns searchset Bundle
GET/Patient/{id}Read one patient as a FHIR Patient resource
POST/PatientImport a FHIR Patient JSON from an external system → creates a new patient with auto-generated MRN

GET/EncounterSearch cases: ?patient= ?status=
GET/Encounter/{id}Read one case as a FHIR Encounter resource
GET/Appointment/{id}Read one appointment as a FHIR Appointment resource
GET/Task/{id}Read one case task as a FHIR Task resource
GET/DocumentReference/{id}Read one document's metadata as a FHIR DocumentReference
Errors are different here
On our normal /api/ routes, errors return RFC 7807 ProblemDetails JSON. On /fhir/R4/ routes, all errors must return a FHIR OperationOutcome resource. This is a FHIR R4 rule — any FHIR client expects this format, so we need a separate exception handler just for the FHIR route prefix.

Patient Import Flow — POST /fhir/R4/Patient

This is the most complex endpoint. An external EHR (or a user pasting JSON in our UI) posts a FHIR Patient resource. We validate it, create the patient in our database, and respond with the created resource including the new MRN.

1

Deserialise with Firely SDK

The raw JSON is parsed by the Firely .NET SDK. If the JSON is not valid FHIR, Firely throws a parse error → we return an OperationOutcome with HTTP 400.

2

Validate the resource

Check that resourceType === "Patient" and that at least one name entry exists. If not → OperationOutcome with HTTP 422.

3

Map FHIR fields → internal Patient

Extract name[0].family → LastName, birthDate → DateOfBirth, etc. Generate a new MRN in MRN-YYYY-NNNNN format.

4

Save to database

Insert into the Patients table via EF Core. The same logic as our PatientDataHandler.CreatePatientAsync.

5

Write FhirImportLogs

Record the full raw FHIR payload, source system, external ID, status (Success), and timestamp. This is our traceability record.

6

Write AuditLogs

Write a standard audit entry: Action = Create, EntityType = Patient, with a note identifying the source system.

7

Return 201 Created

Respond with the newly created patient serialised back to FHIR JSON, including the assigned MRN as the FHIR identifier. Location header points to the new resource URL.

The Angular FhirImportComponent provides a two-step UI: first paste the JSON and preview the parsed fields; then confirm the import. This prevents accidents.

Patient Export — GET /Patient/{id}/$everything

Imagine a patient is transferring from our hospital to a specialist centre. The specialist needs everything: demographics, all their open cases, upcoming appointments, outstanding tasks, and uploaded documents. Instead of printing a 40-page PDF, we hand them a single FHIR Bundle JSON file. Their system imports it directly — no re-typing, no data loss.

When this endpoint is called, we:

  1. Load the Patient from our database
  2. Load all their Cases, Appointments, CaseTasks, and Documents
  3. Map each one to the corresponding FHIR resource type
  4. Package everything into one FHIR collection Bundle
  5. Log the export action to AuditLogs (action: FhirExport)
  6. Return the Bundle JSON

The Angular "Export as FHIR Bundle" button on the Patient Detail page calls this endpoint and triggers a file download named patient-MRN-2026-00001-fhir-bundle.json.

HL7 v2 — the older standard (stretch goal)

HL7 v2 is an older message format from the 1980s still used by many legacy hospital systems (lab machines, radiology systems). Unlike FHIR's clean JSON, HL7 v2 looks like this:

MSH|^~\&|EPIC|HOSPITAL|HCMS|HCMS|20260702120000||ADT^A01|MSG001|P|2.5
PID|||MRN-2026-00001||Smith^Jane^^^||19850322|F|||123 Maple St^^Springfield^IL^62701
If FHIR is a modern REST API with clean JSON, HL7 v2 is a fax machine from 1987. It still works, millions of hospitals still use it, but nobody would design it that way today. We use the NHapi library to parse these messages.

The two stretch-goal endpoints:

  • POST /api/hl7/adt — receives an ADT^A01 (Admit/Register Patient) message and creates/updates the patient record
  • POST /api/hl7/oru — receives an ORU^R01 (Observation Result, i.e. lab results) and attaches it as a case note

Firely .NET SDK — our FHIR toolkit

We use the Firely .NET SDK (Hl7.Fhir.R4 NuGet package). It gives us:

  • Serialiser/Deserialiser — parse incoming FHIR JSON and serialise our objects back to FHIR JSON
  • Strongly-typed models — C# classes like Hl7.Fhir.Model.Patient, Hl7.Fhir.Model.Encounter, etc.
  • Validation — check that a submitted resource conforms to the FHIR R4 spec before we accept it
  • CapabilityStatement builder — helps construct the metadata response
Code sketch: building a FHIR Patient from our entity 
// In FhirMappingService.cs (HCM.Infrastructure)
public Hl7.Fhir.Model.Patient ToFhirPatient(Patient p)
{
    return new Hl7.Fhir.Model.Patient
    {
        Id = p.Id.ToString(),
        Identifier = [ new() {
            System = "https://hcms.example.com/mrn",
            Value  = p.MRN
        }],
        Name = [ new() {
            Family = p.LastName,
            Given  = [ p.FirstName ]
        }],
        BirthDate = p.DateOfBirth.ToString("yyyy-MM-dd"),
        Gender    = MapGender(p.Gender)
    };
}
Why isolate FHIR behind an interface?
The Firely SDK adds ~15 MB of dependencies. We isolate all SDK usage inside IFhirMappingService in HCM.Infrastructure. The Application layer only sees the interface — it never imports Firely directly. This keeps the SDK confined to one layer and means it's only loaded on FHIR request paths.

Developer Responsibilities

Maintaining a FHIR API is not just about writing code. Here is what you need to stay on top of:

AreaWhat to doWhy
FHIR spec complianceRun the free online FHIR validator on your CapabilityStatement and resource responses after any changeA non-compliant response breaks any external FHIR client that calls your API
Status code mappingsWhen adding new case statuses, update the MapCaseStatus() functionFHIR Encounter.status has a fixed set of values — unmapped statuses will cause validation failures
Firely SDK versionKeep the NuGet package updated; watch the changelog for breaking changesNew FHIR profiles and bugfixes ship frequently
FhirImportLogs cleanupAdd a background job to archive logs older than 2 yearsThe RawPayload column stores full FHIR JSON — large payloads accumulate fast
Audit every exportNever skip the AuditLogs write on $everything callsHIPAA requires a record of who accessed patient data and when
OperationOutcome errorsAll errors under /fhir/R4/ must return OperationOutcome, never ProblemDetailsFHIR clients parse OperationOutcome specifically — ProblemDetails will cause silent client failures
Content-Type headerFHIR requests/responses use application/fhir+json, not application/jsonSome FHIR clients reject responses with the wrong content-type

Common gotchas for new developers

Gender enum mismatch
FHIR's Patient.gender only accepts: male, female, other, unknown. Our database might store "M", "Male", or "Non-binary". Your mapping function must handle all variants and fall back to unknown for anything unrecognised. Never return null — the FHIR validator will reject it.
DateTime format
FHIR dates must be YYYY-MM-DD (not DD/MM/YYYY or MM-DD-YYYY). DateTimes must be ISO 8601 with timezone: 2026-07-02T14:30:00+00:00. Always use UTC and always include the timezone offset.
Reference format
When one resource references another (e.g. an Encounter references its Patient), the reference must be in the format "Patient/MRN-2026-00001" — the resource type plus the ID, separated by a slash. A bare GUID is not a valid FHIR reference.
$everything performance
The $everything operation loads a patient plus ALL their related data. For a patient with 10 years of history, this could be hundreds of records. Use AsNoTracking() on all queries, consider adding date range parameters, and set a reasonable response size limit.

AI Integration — RAG on FHIR Data

RAG stands for Retrieval-Augmented Generation. It is the technique of giving an AI language model relevant facts at query time, rather than relying solely on what it learned during training.

Imagine asking a doctor a question. Without context, they can only answer based on their medical training. With RAG, you hand them the patient's full chart before they answer. They use the chart as reference while formulating their response. RAG does the same thing for AI — it retrieves specific records and puts them in the AI's "context window" before it generates a response.

FHIR is ideal for RAG because the $everything Bundle gives you every piece of structured information about a patient in one JSON payload. This is already in a machine-readable, standardised format that AI can consume directly.

How it works with our system

Step 1 — Index FHIR Bundles into a Vector Store

Periodically fetch GET /fhir/R4/Patient/{id}/$everything for each patient. Chunk the Bundle into logical segments (one chunk per Encounter, one per set of Tasks, etc.). Embed each chunk using an embedding model (Azure OpenAI text-embedding-3-small or OpenAI). Store the embeddings in a vector database (Azure AI Search, Pinecone, Weaviate).

  • chunk_id: patient MRN + resource type + resource ID
  • text: human-readable summary of the resource
  • embedding: 1536-dimensional float vector
  • metadata: patientMrn, resourceType, date

Step 2 — Retrieve on query

A care coordinator types: "What were Jane Smith's last three case statuses and any overdue tasks?"

The system: embeds the question → does a similarity search in the vector store filtered by patientMrn = "MRN-2026-00001" → retrieves the 5 most relevant FHIR resource chunks → puts them in the LLM prompt as context.

Step 3 — Generate with an LLM

The LLM (Claude, GPT-4o, etc.) receives the retrieved FHIR chunks as context and generates a precise, factual answer grounded in the actual patient record. No hallucination of facts — everything stated is sourced from real FHIR data.

System: You are a clinical AI assistant. Answer based only on the FHIR data provided.
Context: [retrieved FHIR chunks for MRN-2026-00001]
User: What were Jane's last three case statuses and any overdue tasks?

AI Agents on top of FHIR

An AI Agent goes further than RAG — it can take actions, call tools, and chain multiple steps together. Here are concrete agents we could build on top of our FHIR layer:

🩺

Care Gap Detector

Agent fetches a patient's $everything Bundle, analyses task completion rates, overdue appointments, and last case activity, then generates a "care gap report" with recommended actions.

⚠️

Risk Scorer

Agent reads all Encounters, Tasks (overdue count), and Appointment no-shows for a patient. Calls an LLM to assign a risk score (Low/Medium/High/Critical) with reasoning.

📝

Case Summary Writer

Agent fetches all CaseNotes and Encounters for a case, then generates a structured clinical summary paragraph — useful for handover between coordinators.

🔔

Smart Notifier

Agent monitors the FHIR Task endpoint for overdue tasks, then composes personalised notifications rather than generic "Task overdue" alerts.

📥

FHIR Import Validator

Before importing a FHIR Patient, an AI agent checks for potential duplicate patients by comparing name, DOB, and address against existing records and flags likely matches.

🌐

Cross-System Reconciler

Agent periodically queries an external FHIR server (e.g., a hospital's Epic system), compares data with our internal records, and flags discrepancies for a coordinator to review.

The key insight
Because our FHIR $everything endpoint already produces a perfectly structured, standardised JSON payload for any patient, the "chunker" step is trivial — each top-level resource in the Bundle becomes one chunk. The FHIR standard does the hard structuring work; AI sits naturally on top.
Privacy note
Any AI system processing FHIR patient data must comply with HIPAA. In practice: use Azure OpenAI (not the public OpenAI API) because Microsoft provides a HIPAA BAA (Business Associate Agreement) for Azure services. Never send PHI to the public ChatGPT or OpenAI API without a BAA in place. Never log PHI in AI service request/response logs.

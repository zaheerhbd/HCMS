Why bother testing?

🍳
Imagine a restaurant kitchen. Before a dish goes to a customer, someone tastes it. Not because the chef is bad at cooking — but because it's easy to forget the salt, or grab sugar instead of flour, and nobody notices until a stranger's fork is already in their mouth. Automated tests are that taste-test, except they run in a few seconds, every single time you change the recipe, and they never get tired or distracted.

In HCMS, "the recipe" is code like "when someone logs in with the wrong password five times, lock their account." A human tester would have to type the wrong password five times, by hand, after every single code change, forever. A test does that in under a second and tells you immediately if it ever stops working — for example, if someone edits the login code next year and accidentally breaks the lockout rule.

That's the whole point: tests are a safety net that lets people keep changing the code confidently, without accidentally breaking something that used to work.

🔺

The two kinds of test in this project

HCMS has two test projects, and they check different things:

ProjectWhat it checksCount
HCM.Application.TestsUnit tests — one piece of business logic in isolation43
HCM.API.TestsIntegration tests — the whole app working together over real HTTP26

This shape is called the "testing pyramid": lots of fast, narrow unit tests at the bottom catching small mistakes early, and fewer, slower integration tests near the top confirming the big pieces genuinely fit together.

🧪

Unit tests

🧂
A unit test is like tasting just the sauce before it goes anywhere near the rest of the dish. You're not testing the whole meal — plating, temperature, the side salad — just: "is this one component correct, on its own?"

In HCMS, the "sauce" is a DataHandler — a class that holds one piece of business logic, like AuthDataHandler (login rules) or CaseDataHandler (case status rules). A unit test calls one method on that class directly — no web browser, no HTTP request, no real server — and checks the result.

The one tricky part: the database

DataHandlers talk to the database. Real databases are slow to start up and annoying to reset between tests. So instead of a real SQL Server, unit tests use a lightweight stand-in called EF Core InMemory — it behaves like a real database (you can save, search, filter) but it all just lives in memory and vanishes the instant the test finishes.

🎬
Think of it like a movie stunt double: same moves, same result, but nobody has to risk the real actor (the real production database) to film the scene.

Every unit test in HCMS calls TestDbContextFactory.Create() to get a fresh, empty stunt-double database, all its own, so tests never interfere with each other.

🔍

A real unit test, line by line

Here's an actual test from src/HCM.Application.Tests/Auth/AuthDataHandlerTests.cs. It checks the "5 wrong passwords locks the account" rule.

public async Task LoginAsync_AfterFiveFailedAttempts_LocksAccount()
{
    // 1. Set up a fresh, empty "stunt double" database
    await using var db = TestDbContextFactory.Create();

    // 2. Create a fake user who has already failed 4 times
    var user = NewUser(failedAttempts: 4);
    db.Users.Add(user);
    await db.SaveChangesAsync();

    // 3. Build the real AuthDataHandler — the actual production class,
    //    not a fake — pointed at our stunt-double database
    var sut = new AuthDataHandler(db, new FakeTokenService(), NullLogger<AuthDataHandler>.Instance);

    // 4. Try logging in with the WRONG password — this is the 5th failed attempt
    await Assert.ThrowsAsync<UnauthorizedAccessException>(
        () => sut.LoginAsync(user.Username, "WrongPassword!"));

    // 5. Check the account actually got locked
    var reloaded = await db.Users.FindAsync(user.Id);
    reloaded!.FailedLoginAttempts.Should().Be(5);
    reloaded.IsLockedOut.Should().BeTrue();
}
1
Every test starts with a brand-new, empty database, so nothing left over from a previous test can sneak in and cause a false result.
2
We plant a fake user who's already failed 4 times — one more failure should trip the lockout.
3
sut stands for "system under test" — a common naming convention. This is the real AuthDataHandler class from the actual application, not a fake version — that's the whole point of a unit test: prove the real logic works.
4
We attempt a login we know is wrong, and assert (fancy word for "check") that it throws the expected error.
5
Finally we re-read the user from the database and confirm the account is now actually locked — proving the rule didn't just throw an error, it also recorded the lockout correctly.
✅
If someone later "simplifies" the lockout logic and accidentally changes it to lock after 10 attempts instead of 5, this test immediately turns red and tells them exactly what broke — instead of a real user getting silently locked out (or not locked out) in production months later.
🔗

Integration tests

🎭
If a unit test is tasting the sauce alone, an integration test is a full dress rehearsal: real actors, real costumes, real stage — everyone performing together, in order, exactly like opening night. You're not checking one ingredient anymore; you're checking that the whole show actually works end to end.

An integration test in HCMS starts the real web application — the same Program.cs, the same controllers, the same login/security rules — and sends it real HTTP requests, exactly like a browser or Postman would. It checks things a unit test can't, such as: "does a request with no login token actually get rejected by the security layer?" or "does a Care Coordinator's role actually let them create a patient, while a Read-Only user gets blocked?"

What's swapped out, and why

Two things are still too slow or unavailable to use for real in a test run, so they're replaced with lightweight stand-ins — everything else is 100% the real production code:

Real thingStand-in used in testsWhy
SQL Server databaseEF Core InMemoryNo database server needs to be installed or started just to run tests
Azure Blob Storage (file uploads)A fake in-memory blob serviceTests shouldn't need a real Azure account or internet connection
⚠️
The original Phase 8 plan called for a real, temporary SQL Server running in Docker (a tool called Testcontainers) instead of the InMemory stand-in above — that's even closer to production. Docker's engine wasn't running in this dev environment, so InMemory was used instead. Everything else (the security rules, the controllers, the actual HTTP pipeline) is unchanged, real code.
🔍

A real integration test, line by line

From src/HCM.API.Tests/Auth/AuthFlowTests.cs — checks that logging in gives you a working "key" (token) that actually unlocks a protected page.

public async Task Login_ThenAccessProtectedRoute_Succeeds()
{
    // 1. Spin up a real copy of the HCMS API in memory
    var client = _factory.CreateClient();

    // 2. Send a real HTTP login request, just like the Angular app would
    var login = await client.PostAsJsonAsync("/api/auth/login", new LoginRequest("admin", "Admin@123!"));
    var auth = await login.Content.ReadFromJsonAsync<AuthResponseDto>();

    // 3. Attach the access token we got back, like a browser would after login
    client.DefaultRequestHeaders.Authorization =
        new AuthenticationHeaderValue("Bearer", auth!.AccessToken);

    // 4. Now try to reach a page that requires being logged in
    var protectedResponse = await client.GetAsync("/api/cases");

    // 5. It should succeed — 200 OK — because we're properly logged in
    protectedResponse.StatusCode.Should().Be(HttpStatusCode.OK);
}
1
_factory.CreateClient() boots up the actual web app — controllers, security middleware, everything — and gives us something that behaves exactly like a web browser talking to it.
2
We send a real login request over (in-memory) HTTP, using the same username/password an actual person would type in.
3
Logging in returns an access token — like a wristband at a concert. We attach it to every future request, the same way the Angular app does.
4
/api/cases is a page that refuses anyone without a valid wristband. We try to visit it.
5
Because we have a valid, freshly issued token, the server lets us in — 200 OK. A companion test (Login_WithoutToken_OnProtectedRoute_Returns401) proves the opposite: no wristband, no entry.
⚖️

Unit vs. Integration, side by side

🧪 Unit test

  • Tests one class in isolation
  • No real HTTP, no security layer
  • Runs in milliseconds
  • Pinpoints exactly which piece of logic broke
  • Example: "does the MRN number generator produce MRN-2026-00001?"

🔗 Integration test

  • Tests the whole app working together
  • Real HTTP requests, real security/login rules
  • Runs in a few seconds
  • Confirms the pieces are actually wired together correctly
  • Example: "can a Read-Only user really not create a patient through the API?"
🧩
You need both. A jigsaw puzzle can have every single piece individually perfect (unit tests passing) and still not form a picture if two pieces don't actually click together (which only an integration test would catch) — say, if the login page sends the token in a slightly different format than the security layer expects to receive it.
🐞

A real bug this testing effort caught

Writing the auth integration test above led to something worth knowing about: two related endpoints, POST /api/auth/refresh and POST /api/auth/logout, turned out to just be placeholders in the code — literally marked // TODO — that always return a canned response and don't do any real work.

// src/HCM.API/Controllers/AuthController.cs
[HttpPost("refresh")]
public async Task<IActionResult> Refresh([FromBody] RefreshRequest request, CancellationToken ct)
{
    // TODO: Implement RefreshTokenService
    return Unauthorized();
}

This wasn't caught by a failing test — it was caught by the act of trying to write a realistic login → refresh → logout test and discovering there was nothing real to test. That's filed as GitHub issue #5 so it gets fixed properly later, instead of being silently forgotten.

💡
This is a good example of a broader truth: tests don't just catch bugs in existing code — the process of writing them forces you to actually use every code path the way a real user would, which surfaces gaps nobody had gotten around to finishing yet.

Running the tests yourself

# from the src/ folder
dotnet test HCM.Application.Tests\HCM.Application.Tests.csproj   # unit tests
dotnet test HCM.API.Tests\HCM.API.Tests.csproj                   # integration tests

# or run everything in the solution at once
dotnet test

Each run takes a few seconds. A green "Passed!" line at the end means every check succeeded; anything red names the exact test and the exact expectation that failed.

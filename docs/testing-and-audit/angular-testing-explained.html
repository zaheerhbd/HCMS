Why bother testing the frontend?

🚦
Think of the Angular app as a car dashboard. The dashboard itself doesn't drive the car — the engine (the API) does that — but if the fuel gauge lies, or the seatbelt light stays off when it shouldn't, the driver makes bad decisions even though the engine was fine the whole time. Frontend tests check the dashboard: does it show the right thing, does it lock out the wrong thing, does it recover correctly when something goes wrong.

In HCMS, the "dashboard" is things like: does the login screen actually attach my session key to every request? and if my session key expires mid-use, does the app quietly renew it instead of kicking me out? Nobody wants to test that by hand — log in, wait for the token to expire, click around, watch the network tab — every single time someone touches that code. A test does it in a fraction of a second.

📋

What exists today

Six spec files cover the pieces of the Angular app that hold real logic — services, an interceptor, form validation, and a role-based visibility directive. Purely visual components (that just bind data to HTML) are intentionally left alone; there's very little that could go subtly wrong in them, so testing them has low payoff.

Unit tests, in Angular

🧂
Same idea as the backend: taste just the sauce, not the whole meal. A unit test calls one method on one class and checks what comes back — no real browser page, no real server.

The one thing every Angular service in HCMS depends on is HttpClient — the thing that actually sends network requests. Real network requests are slow and need a real backend running. So tests use HttpClientTestingModule, a stand-in that intercepts every outgoing request and lets the test decide exactly what response comes back, instantly, with no network involved.

🎬
It's the same stunt-double idea as the backend's in-memory database — a fake network that behaves close enough to the real one to test against, but with zero setup and zero risk.
🔍

A real unit test, line by line

From src-ng/hcm-web/src/app/core/services/auth.service.spec.ts — checks that logging in actually saves the session in localStorage.

it('login() should store tokens, username, and roles in localStorage', () => {
  // 1. Call the real login() method — nothing is faked here
  service.login({ username: 'jdoe', password: 'secret' }).subscribe();

  // 2. Intercept the outgoing request the service just made
  const req = httpMock.expectOne(`${environment.apiUrl}/auth/login`);
  expect(req.request.method).toBe('POST');

  // 3. Hand back a fake — but realistic — server response
  req.flush(mockResponse);

  // 4. Now check the service actually saved everything it should have
  expect(localStorage.getItem('hcms_access_token')).toBe(mockResponse.accessToken);
  expect(localStorage.getItem('hcms_refresh_token')).toBe(mockResponse.refreshToken);
  expect(JSON.parse(localStorage.getItem('hcms_roles')!)).toEqual(mockResponse.roles);
});
1
We call the actual, real AuthService.login() — the same code that runs when a real person clicks "Sign In".
2
httpMock.expectOne(...) catches the network request before it goes anywhere and confirms the service asked for exactly the right URL, with the right HTTP method.
3
req.flush(...) is the test playing the part of the server — handing back a canned, realistic response instead of hitting a real backend.
4
We then check localStorage directly, proving the service's side effect (saving the session) actually happened, not just that it didn't crash.
✅
If someone later renames a localStorage key, or forgets to save the roles array, this test fails immediately — instead of someone discovering weeks later that role-based menus are broken for every user.
🔍

An interceptor test, line by line

From jwt.interceptor.spec.ts — the trickiest test in the set, because it checks a two-step recovery: a token expires mid-request, and the app has to quietly fix it and retry, instead of showing the user an error.

it('should refresh the token and retry the original request on a 401', () => {
  spyOn(authService, 'getAccessToken').and.returnValue('expired.token');
  spyOn(authService, 'refreshToken').and.returnValue(of(refreshResponse));

  // 1. Kick off a normal request, as if a component just asked for patient data
  http.get('/api/patients').subscribe(res => (result = res));

  // 2. Pretend the server rejected it — the token had just expired
  const firstReq = httpMock.expectOne('/api/patients');
  firstReq.flush({ message: 'expired' }, { status: 401, statusText: 'Unauthorized' });

  // 3. The interceptor should have automatically asked for a new token,
  //    then silently retried the SAME request with it
  const retriedReq = httpMock.expectOne('/api/patients');
  expect(retriedReq.request.headers.get('Authorization')).toBe('Bearer new.token');
  retriedReq.flush({ ok: true });

  // 4. The component that made the original call never even knows this happened
  expect(result).toEqual({ ok: true });
});
1
Something in the app asks for data, completely unaware that its saved token happens to be expired.
2
We simulate the server's real reaction to an expired token: 401 Unauthorized.
3
The interceptor is supposed to catch that 401, fetch a fresh token behind the scenes, and re-send the exact same request with it — all without the caller doing anything extra.
4
The final check proves the whole dance worked: the original caller just gets its data, as if nothing ever went wrong.
💡
A companion test proves the interceptor doesn't try to refresh when the 401 comes from the refresh endpoint itself — otherwise a truly dead session would refresh-fail-refresh-fail forever in an infinite loop instead of logging the user out.
🧩

Component tests — Angular's "grey area"

The case-form and patient-form specs sit between the two worlds. They don't call one function in isolation — they use TestBed.createComponent() to build the real component with its real Reactive Form, then poke at the form directly:

component.form.patchValue({ firstName: 'Jane', lastName: 'Doe', dateOfBirth: new Date('1990-01-01') });
expect(component.form.valid).toBeTrue();

This is technically still a "unit" test — no browser, no real navigation, no real server — but it's testing several things wired together at once (the form group, its validators, the component class), which is a little more than the pure single-function tests above. That's normal, and it's why Angular's own docs sometimes call these "shallow" component tests.

⚠️
The patient-form spec deliberately includes a test that documents a known gap: a date of birth in the future currently passes validation, because there's no max-date rule yet. The test doesn't hide that — it asserts the current (imperfect) behavior with a comment explaining why, so whoever adds that validator later gets an honest signal instead of a silent surprise.
🔗

Real integration testing — where it actually happens

🎭
Unit tests taste the sauce. A true integration test is the full dress rehearsal — a real browser, pointed at the real running app, clicking through it exactly like a person would.

Angular's TestBed can render a component, but it never opens an actual browser tab or talks to a real running backend. For HCMS, genuine end-to-end integration testing — login → create a patient → create a case → upload a document — is a separate layer built with Playwright, driving a real Chromium browser against the real Angular dev server and the real API.

FlowWhat it proves

💡
This is documented in e2eplaywright.md as the planned next layer — it hasn't been built yet. The 32 unit tests above are the foundation; Playwright is what would catch a bug like "the login page sends the token in a format the interceptor doesn't expect" — something no unit test alone can see, because each side is tested in isolation from the other.
⚖️

Three layers, side by side

🧪 Unit test exists — 32 passing

  • Tests one service, interceptor, directive, or form in isolation
  • Network faked with HttpClientTestingModule
  • Runs in well under a second, all 32 together
  • Example: "does an expired token trigger exactly one silent refresh?"

🧩 Component test exists — included above

  • Renders a real component + real form together
  • Still no browser, still no real server
  • Example: "is the case form invalid until patientMrn and caseTypeId are filled?"

🔗 End-to-end (Playwright) planned, not yet built

  • Real Chromium browser, real Angular dev server, real API
  • Confirms the frontend and backend are actually wired together correctly
  • Example: "can a real user log in, create a patient, and see its MRN on screen?"
▶️

Running the tests yourself

# from src-ng/hcm-web/
npx ng test --watch=false --browsers=ChromeHeadless

# same thing, plus a coverage report (coverage/hcm-web/index.html)
npx ng test --watch=false --browsers=ChromeHeadless --code-coverage

Each run takes about a second. A green "SUCCESS" total means every check passed; a failure prints the exact test name and the exact expectation that didn't hold.

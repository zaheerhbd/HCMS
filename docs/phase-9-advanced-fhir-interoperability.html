🏥 What Was Built

1 · FHIR Transaction Bundle Import (POST /fhir/R4/)

A single HTTP request carries a complete patient intake package — Patient, Encounter (case), Appointments, and Tasks — as a FHIR Transaction Bundle. The server processes entries in order, resolves internal urn:uuid: references, and either commits everything or rolls back to zero on any failure. The response is a valid FHIR transaction-response Bundle with the assigned ID for each created resource.

Real-life analogy

A Transaction Bundle is like a multi-item cart checkout: either every item ships or nothing is charged. You never end up with a patient record but no case, or a task pointing at a case that was never created.

2 · FHIR Bundle File Upload (POST /fhir/R4/$import)

A dedicated multipart/form-data endpoint accepts a .json bundle file directly. The server reads the file via IFormFile, then delegates to the same ImportTransactionBundleAsync logic — identical atomicity guarantees, different intake path. This enables users to upload a file they already have on disk without copying JSON into a textarea.

3 · Angular Drag-and-Drop Import UI

The "Import Bundle" tab was rebuilt around a drag-and-drop file upload zone as the primary path. A "or paste JSON" textarea fallback remains for programmatic or sample-driven use. Uploading a file calls POST /fhir/R4/$import; pasting JSON calls POST /fhir/R4/. Both paths show the same per-entry result table on success.

📦 Transaction Bundle — Backend Design

POST /fhir/R4/ — accepts Content-Type: application/fhir+json with raw Bundle JSON. Returns a transaction-response Bundle on success or OperationOutcome on failure.

Processing flow

1
Parse & validateFhirMappingService.ParseTransactionBundle uses the Firely SDK to deserialize the Bundle and extract each entry into clean ParsedBundleEntry records. No Firely types cross the Application boundary.
2
Open EF Core transactionIApplicationDbContext.BeginTransactionAsync wraps all subsequent writes. All child handlers share the same scoped DbContext and participate automatically.
3
Process in order: Patient → Encounter → Appointment → TaskEach entry is created via its existing DataHandler. Assigned IDs are captured in urnMap as each resource is created.
4
Resolve urn:uuid: referencesCross-entry references like urn:uuid:patient-1 are resolved to real assigned IDs (e.g. Patient/MRN-2026-00042) via the ResolveId helper.
5
Write logs and commitOne FhirImportLog per resource type + one AuditLog written inside the transaction, then CommitAsync.
6
Rollback on any exceptionAny failure triggers tx.RollbackAsync(). Zero rows written. Response: OperationOutcome with the error message.

📁 FHIR Bundle File Upload

POST /fhir/R4/$import — accepts Content-Type: multipart/form-data with a form field named bundleFile containing a .json file. Reads the file server-side via IFormFile, then delegates to the same ImportTransactionBundleAsync — identical atomicity, same response format.

Real-life analogy

Think of the two endpoints like two ways to submit a form: you can type directly into a web portal (JSON body) or upload a pre-filled PDF you already have on disk (file upload). The back-office processing is identical — only the intake mechanism differs.

Validation

  • File must have .json extension or Content-Type containing "json" — returns OperationOutcome otherwise
  • File must not be empty — returns 400 if IFormFile.Length == 0
  • File content read with StreamReader server-side — no client memory required for large files

Controller

[HttpPost("$import")]
[Consumes("multipart/form-data")]
public async Task<IActionResult> UploadTransactionBundle(IFormFile bundleFile, CancellationToken ct)
{
    if (bundleFile == null || bundleFile.Length == 0)
        return BadRequest(FhirOperationOutcome("invalid", "Request must include a bundleFile (.json)."));

    string bundleJson;
    using (var stream = bundleFile.OpenReadStream())
    using (var reader = new StreamReader(stream))
        bundleJson = await reader.ReadToEndAsync(ct);

    var userId = User.FindFirst(ClaimTypes.NameIdentifier)?.Value ?? "unknown";
    var result = await _handler.ImportTransactionBundleAsync(bundleJson, userId, ct);
    // ... identical response logic as POST /fhir/R4/
}

Angular service

uploadBundleFile(file: File): Observable<FhirBundleImportResult> {
  const formData = new FormData();
  formData.append('bundleFile', file);
  // No Content-Type header — browser adds multipart boundary automatically
  return this.http.post<FhirBundleImportResult>(`${this.base}/$import`, formData);
}

🔒 Atomicity Deep-Dive

A partial write is worse than no write. If a Patient is created but the Case fails, the system has an orphaned record and a coordinator who can't find the patient. The FHIR spec mandates all-or-nothing semantics for Transaction Bundles.

All DataHandlers are registered as scoped services — they share the same IApplicationDbContext per HTTP request. When FhirDataHandler calls BeginTransactionAsync, all subsequent SaveChangesAsync calls across all child handlers participate in the same uncommitted SQL Server transaction. One CommitAsync or RollbackAsync covers everything.

Transaction flow across multiple DataHandlers 
await using var tx = await _db.BeginTransactionAsync(ct);
try {
    var patient = await _patientHandler.CreatePatientAsync(...);        // SaveChanges #1
    var cas     = await _caseHandler.CreateCaseAsync(...);             // SaveChanges #2
    var appt    = await _appointmentHandler.CreateAppointmentAsync(...); // #3
    var task    = await _taskHandler.CreateTaskAsync(...);             // #4
    _db.FhirImportLogs.Add(...);
    _db.AuditLogs.Add(...);
    await _db.SaveChangesAsync(ct);                                    // #5
    await tx.CommitAsync(ct);    // only this line makes anything permanent
}
catch {
    await tx.RollbackAsync(ct);  // every row from #1-#5 vanishes
    throw;
}

🔗 urn:uuid: Reference Resolution

Bundle entries reference each other before any are persisted. An Encounter references urn:uuid:patient-1 — a Patient that only exists in the same bundle. After the Patient is created as MRN-2026-00042, that reference must resolve to Patient/MRN-2026-00042 for all subsequent entries.

// After Patient created:
urnMap["urn:uuid:patient-1"] = "Patient/MRN-2026-00042";

// ResolveId("Patient", "urn:uuid:patient-1", urnMap)
//   looks up urnMap, splits on "/", returns "MRN-2026-00042"

The ResolveId helper handles three reference forms: urn:uuid:xxx (via urnMap), ResourceType/Id (direct split), or null (fallback to first created resource of the target type).

⚖ Key Decisions & Trade-offs

1 · Two endpoints, one handler

Decision: Both intake paths delegate to the same ImportTransactionBundleAsync. The controller reads a plain string from either body or file, then calls the handler.

Why: Avoids duplicating business logic. The handler has no concept of how the JSON arrived — atomicity, validation, and logging are guaranteed identically for both paths.

2 · No Content-Type header on FormData upload from Angular

Decision: uploadBundleFile does not set a Content-Type header manually when posting FormData.

Why: The browser auto-generates multipart/form-data; boundary=... including the boundary token. Setting it manually would omit the boundary, breaking multipart parsing on the server.

3 · Firely SDK stays in Infrastructure

Decision: ParseTransactionBundle returns plain ParsedBundleEntry records with no Firely types.

Why: Application layer stays SDK-independent. Handlers are unit-testable without Firely; the parsing library can be swapped without touching business logic.

4 · Child handlers invoked (not direct DbContext writes)

Decision: FhirDataHandler calls existing child handlers rather than writing directly to _db.

Why: Child handlers contain all validation (MRN generation, duplicate detection). Since all share the same scoped DbContext, they participate in the parent transaction automatically.

5 · Default provider fallback for Appointments

Decision: When an Appointment entry has no recognized practitioner reference, the system uses the first active Provider rather than failing.

Why: External bundles often omit provider IDs. A soft fallback lets intake succeed; the coordinator updates the assignment later. Failing hard would reject too many real-world bundles.

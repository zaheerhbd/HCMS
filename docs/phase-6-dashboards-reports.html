Overview

Phase 6 adds the data-visibility layer of HCMS: every role now has a purpose-built dashboard showing the metrics most relevant to their work, and administrators can download structured reports for offline analysis.

Real-world analogy
Think of the dashboards as the instrument cluster in a car — the coordinator sees their lane (their own cases and overdue tasks), the supervisor sees the whole convoy (team caseloads across coordinators), and the admin sees the fleet management system (system-wide stats, login trends, imports). Each view is tailored so drivers only see dials relevant to their seat.

Three report types give managers a printable or spreadsheet-ready snapshot: case distribution by status, average open-to-close duration grouped by case type, and task completion rates by assignee.

Architecture

Phase 6 follows the same Clean Architecture layers as every other phase: the Application layer owns DataHandlers and DTOs; the Infrastructure layer owns the DB context; the API layer owns controllers; Angular owns the presentation.

Layer diagram — Phase 6 data flow

Dashboard and report data flows top-to-bottom through layers. The Angular service makes one HTTP call; the controller authenticates the request, checks the role, and forwards to the DataHandler; the DataHandler runs EF Core queries against IApplicationDbContext and returns typed DTOs. No business logic leaks into controllers or Angular services.

Backend Implementation

Dashboard DataHandler

DashboardDataHandler implements IDashboardDataHandler with three methods, each scoped to a role's information needs.

Why three separate methods instead of one big method with a role parameter?
Each role genuinely needs different entities. Merging them into one method would load unnecessary data for two of three callers on every request — wasteful and harder to reason about. Separation also means the access-control boundary is at the controller level, not buried in a conditional inside the handler.
GetCoordinatorDashboardAsync — implementation detail

Queries run concurrently (conceptually) against five DbSets:

  • Open case count — Cases WHERE IsActive AND AssignedToUserId == userId
  • Cases by status — GroupBy(CurrentStatus) → CaseStatusCountDto list
  • Overdue tasks — CaseTasks WHERE AssignedTo == userId AND DueDate < now AND Status != Done, top 10
  • Today's appointments — Appointments WHERE ScheduledStart >= today AND ScheduledStart < tomorrow, top 10
  • Inactive case count — open cases where UpdatedAt < now - 7 days

Entity field names: Case.AssignedToUserId (Guid?), Appointment.ScheduledStart (DateTime), CaseTask.AssignedTo (Guid?).

GetSupervisorDashboardAsync — implementation detail

Because Case has no EF navigation to User (only the FK AssignedToUserId), the supervisor method loads assignee names via a separate dictionary lookup:

  1. Load all active open cases → collect distinct AssignedToUserId values
  2. Query Users WHERE Id IN (assigneeIds) → build Dictionary<Guid, string>
  3. Group cases client-side to build UserCaseloadDto rows
  4. Separately load escalated cases and inactive cases (those not updated in 7+ days)

This avoids a cross-table join that EF would need to translate without a navigation property, keeping queries simple and observable.

GetAdminDashboardAsync — implementation detail

Seven scalar queries plus one grouped query for login trend:

  • Active users, total patients, total cases, open cases — four CountAsync calls
  • Logins last 7 days — RefreshTokens WHERE CreatedAt >= 7DaysAgo, distinct userId count
  • FHIR imports last 30 days — FhirImportLogs WHERE ImportedAt >= 30DaysAgo count
  • Daily login trend — one query per day (7 iterations), each counting distinct user logins per 24-hour window
  • Users by role — UserRoles.GroupBy(ur => ur.Role.Name)

The one-query-per-day loop is intentional for a dashboard endpoint (called rarely, result easily cached if needed). Replacing it with a single raw-SQL GROUP BY would break the no-raw-SQL policy.

Report DataHandler

ReportDataHandler provides six methods: three returning typed DTOs (for JSON responses) and three returning RFC 4180 CSV strings.

Design decision: client-side duration calculation
The case-duration report needs DATEDIFF(day, CreatedAt, ClosedAt). EF.Functions.DateDiffDay is SQL Server-specific and lives in the Infrastructure layer — using it directly in Application would violate the Clean Architecture dependency rule (Application must not depend on SQL Server). Solution: project CreatedAt and ClosedAt as raw DateTime values via LINQ, call ToListAsync(), then compute (ClosedAt - CreatedAt).TotalDays in C# memory. For report volumes (<10k rows) this is perfectly acceptable.
CSV generation — EscapeCsv helper 
private static string EscapeCsv(string value)
{
    if (value.Contains(',') || value.Contains('"') || value.Contains('\n'))
        return $"\"{value.Replace("\"", "\"\"")}\"";
    return value;
}

RFC 4180 requires fields containing commas, double-quotes, or newlines to be wrapped in double-quotes, with embedded double-quotes doubled. No third-party library needed for the three simple report shapes in this phase.

Angular Frontend

Dashboard Hub Component

DashboardComponent acts as a role-based dispatcher. On init it iterates a priority list (Admin → Supervisor → CareCoordinator → Clinician → ReadOnly) and renders the first matching role's sub-component using Angular's @if control flow. This keeps routing simple (one /dashboard route) while delivering a fully tailored experience per role.

Admin Dashboard

Six stat cards cover system-wide metrics. Two Chart.js charts occupy the lower half of the page:

  • Line chart — daily distinct login count for the past 7 days (login-trend data from RefreshTokens)
  • Bar chart — user count per role (Admin, Supervisor, CareCoordinator, Clinician, ReadOnly)

Both charts are registered with minimal Chart.js tree-shaking: only the controllers and elements actually used are imported, keeping bundle impact low.

CSV download implementation in Angular 
// ReportService.downloadCsv()
downloadCsv(endpoint: string, filename: string): void {
  this.http.get(`${this.base}/${endpoint}?format=csv`, {
    responseType: 'blob',
    headers: { Accept: 'text/csv' }
  }).subscribe(blob => {
    const url = URL.createObjectURL(blob);
    const a = document.createElement('a');
    a.href = url; a.download = filename; a.click();
    URL.revokeObjectURL(url);
  });
}

No FileSaver.js or other third-party library. The blob response type bypasses Angular's default JSON parsing; the anchor-click trick triggers a native browser download dialog.

Chart.js Integration

Chart.js 4.5.1 was installed directly via npm. The decision not to use ng2-charts (the popular Angular wrapper) was deliberate:

Considerationng2-charts wrapperDirect Chart.js
Bundle overheadWrapper adds ~15 kBZero wrapper overhead
Angular version supportLagged behind Angular 19 at time of buildNo Angular dependency at all
Chart update patternInput-driven, change-detection coupledImperative chart.update() — full control
Tree-shakingFull Chart.js bundleOnly import used controllers/elements
Learning value (portfolio)Hides Chart.js APIDemonstrates raw Chart.js competence

Each chart component follows this lifecycle pattern:

  1. @ViewChild('myCanvas') canvasRef!: ElementRef<HTMLCanvasElement>
  2. Load data in ngOnInit()
  3. Build chart in ngAfterViewInit() after data arrives (or destroy + recreate on data change)
  4. Destroy the chart instance in ngOnDestroy() to avoid canvas re-use errors
Common Chart.js pitfall avoided
If you navigate away and back to a route, Angular destroys and re-creates the component. Without calling chart.destroy() in ngOnDestroy(), Chart.js caches the old canvas context and throws "Canvas is already in use." All six chart components in this phase include proper destroy logic.

CSV Export Design

All three CSV reports are built server-side in ReportDataHandler using a StringBuilder and the EscapeCsv helper. This avoids any dependency on CsvHelper or similar libraries — the report shapes are simple, static schemas that don't need reflection-driven serialization.

Example CSV output — Tasks by Assignee 
User,Total Tasks,Done,Overdue,Open,In Progress
Alice Coordinator,12,8,1,2,1
Bob Clinician,7,4,0,3,0
Carol Supervisor,5,5,0,0,0

The Content-Disposition: attachment header on the API response ensures browsers don't try to render the CSV inline — they trigger a file-save dialog directly.

Bug Fixes in This Phase

1. ApplicationDbContext.BeginTransactionAsync not implemented

Error: CS0535: 'ApplicationDbContext' does not implement interface member 'IApplicationDbContext.BeginTransactionAsync'

Root cause: The interface declaration was added during Phase 7 (for the notification transactional write), but the concrete class in Infrastructure never received the implementation.

Fix: Added to ApplicationDbContext.cs:

public Task<IDbContextTransaction> BeginTransactionAsync(CancellationToken ct = default)
    => Database.BeginTransactionAsync(ct);

2. NHapi package version 4.* does not exist on NuGet

Error: NU1102: Unable to find package NHapi.Base with version (>= 4.0.0)

Root cause: Phase 7 added NHapi.Base and NHapi.Model.V251 with Version="4.*". NHapi's latest published version on NuGet is 3.x; version 4 does not exist.

Fix: Changed to Version="3.*" in HCM.Infrastructure.csproj. No C# code references NHapi directly yet (the HL7 parsing service is interface-only in Application; the implementation is deferred to Phase 9), so no code changes were needed.

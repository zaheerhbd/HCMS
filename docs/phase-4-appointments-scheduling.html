What Was Built

Phase 4 introduces a full appointment scheduling system. A care coordinator can book an appointment for a patient with a specific provider, choosing a time slot and appointment type. The system validates that the provider is not already booked for any overlapping time — the conflict detection feature prevents double-booking.

Appointments move through a defined status lifecycle (Scheduled → Confirmed → Completed / NoShow / Cancelled). A background IHostedService scans for upcoming appointments within 24 hours and queues notification rows to alert the care coordinator.

The Angular module has three standalone components: a filterable list view, a booking form with conflict error display, and a detail view with status action controls.

Conflict Detection

The core scheduling rule: a provider cannot have two overlapping appointments. The DataHandler validates this on both create and reschedule using an EF LINQ query.

Overlap detection query logic

Two time slots overlap if: existingStart < newEnd AND existingEnd > newStart. In LINQ:

bool conflict = await _db.Appointments.AnyAsync(a =>
    a.ProviderId == providerId &&
    a.Id != appointmentId &&  // exclude self on reschedule
    a.Status != "Cancelled" &&
    a.ScheduledStart < scheduledEnd &&
    a.ScheduledEnd > scheduledStart);

If a conflict is found, the DataHandler throws a ValidationException with the message "Provider already has an appointment during this time slot." The controller maps this to a 422 Unprocessable Entity response. The Angular form checks for this specific message string and shows it inline (not as a toast) so the user can see it while adjusting the time.

Appointment Reminder Service

AppointmentReminderService (IHostedService)

Runs every 15 minutes. Queries appointments where Status = 'Scheduled' OR Status = 'Confirmed' AND ScheduledStart is between now and now + 24h AND ReminderSentAt IS NULL. For each match:

  1. Creates a Notification row for the assigned care coordinator.
  2. Sets ReminderSentAt = NOW() on the appointment to prevent duplicate notifications.

The Notifications table is polled by the Angular NotificationBellComponent every 60 seconds (Phase 7). Phase 4 only creates the rows — the UI bell is wired in Phase 7.

Analogy: Think of it like a hospital receptionist who checks the appointment book every 15 minutes and calls patients to confirm tomorrow's appointments. The ReminderSentAt flag is their checkmark next to each patient's name — they won't call the same patient twice.

AppointmentListComponent

Lazy-loaded at /appointments. Shows all appointments with filtering and pagination.

Component details
  • Page header: "Appointments" title + "Schedule Appointment" button (CareCoordinator+ only, via *appHasRole).
  • Status filter mat-select (debounced 300ms) — blank = all statuses.
  • mat-table columns: patient (name + MRN sub-text), provider, appointment type, scheduled start (date + time range), status chip (colour-coded), chevron action column.
  • Status chips are colour-coded via statusBg() / statusColor() helper methods using STATUS_COLORS constant.
  • mat-paginator with page size options.
  • Row click navigates to /appointments/{id}.

AppointmentFormComponent

Route: /appointments/new. A card-wrapped Reactive Form for scheduling a new appointment.

Form fields
  • Patient MRN (required) — free-text input; server resolves to patient.
  • Case Number (optional) — links appointment to a case for case-centric tracking.
  • Provider (required) — dropdown populated from GET /api/appointments/providers; shows specialty as hint text below the selection.
  • Appointment Type (required) — Initial Assessment / Follow-Up / Specialist Referral / Telehealth.
  • Scheduled Start and End (required) — datetime-local inputs; converted to ISO 8601 UTC before POST.
  • Location (optional) — room number or telehealth link.
  • Notes (optional) — multiline textarea.
Conflict error display

When the server returns a 422 with a message containing "already has an appointment", the form sets conflictError and renders a red inline error banner with a warning icon. This is shown inline (not as a toast) because the user needs to see it while adjusting the Start/End times without the message disappearing after 3 seconds.

UX decision: Toasts auto-dismiss. A conflict error requires the user to take action (change the time) before submitting again. Inline errors are persistent until the user corrects the input and resubmits — which is the correct behaviour for a recoverable validation failure.

AppointmentDetailComponent

Route: /appointments/{id}. Shows full appointment details and allows status changes.

Component details
  • Breadcrumb: Appointments → #{id}
  • mat-card with a two-column detail-grid: patient name, provider, start, end, location, case link (if linked), notes.
  • Status change section (CareCoordinator+ only): mat-select for new status + Apply button. Only shown if the appointment is not terminal (Completed / Cancelled).
  • On status change: optimistic update of the displayed status; snack bar confirmation.
  • Back button navigates to /appointments.

Key Decisions & Trade-offs

DecisionChosenRejectedReason
Conflict detection timing Server-side on every create/reschedule Client-side only Two coordinators could book the same slot simultaneously — a race condition the client can't detect. The server query runs under a short-lived transaction to minimise the window.
Conflict error UX Inline persistent error banner Toast notification Toasts auto-dismiss after 3–4 seconds. The user needs to adjust Start/End time fields while the error is still visible — an inline error stays until the form is resubmitted.
Reminder mechanism Background IHostedService + Notifications table rows SendGrid / email directly from background service In-app notifications are simpler for a portfolio project (no external SMTP dependency). The Notifications table is already there from Phase 2; Phase 7 will wire the notification bell.
Provider model Separate Providers entity with optional UserId FK Reuse the Users table directly Not all providers are system users (external consultants). A dedicated Provider entity is more flexible and avoids coupling scheduling logic to auth users.
Appointment routing GUID-based (not a business key) Appointment number slug Appointments don't have a natural, memorable business key like MRN or CaseNumber. A GUID is acceptable here because appointments are navigated from a list, not typed directly into URLs.

Security Notes

  • All endpoints require authentication — no public appointment data
  • Create/reschedule/status-change restricted to CareCoordinator, Supervisor, Admin
  • Read access (GET) available to all authenticated roles (Clinicians need to see appointments for their patients)
  • Conflict detection prevents overbooking even if two coordinators submit simultaneously (server-side query)
  • Cancelled/Completed appointments cannot transition to any new status (terminal state machine)
  • No PHI logged — only appointment IDs and user IDs are written to Application Insights
  • Provider availability endpoint exposes only busy time slots, not PHI about the patients booked in those slots

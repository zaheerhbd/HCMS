Why Notifications?

In a case management system, coordinators handle dozens of patients simultaneously. Without notifications, a clinician assigned a task must manually check the task list. A coordinator whose case just escalated won't know until their next login. A daily check-in model creates delays that matter in healthcare.

Real-world analogy — Pager vs. chart rounds: Before smartphones, doctors relied on pagers to know when something needed immediate attention. Browsing the task list without notifications is like doing chart rounds every hour hoping to spot changes — you will miss things. The notification bell is the pager: it surfaces events the moment they happen, so the right person can act.

The audit log viewer addresses a different need: compliance and accountability. HIPAA requires that every access and modification to PHI be traceable to a specific user with timestamp. The existing AuditInterceptor was already capturing this — Phase 7 adds the UI and API to make it queryable by admins.

Real-world analogy — Hospital security footage: An audit log without a viewer is like a hospital that records all security footage but has no playback terminal. The data is there — you just can't act on it until someone builds the viewing interface.

Notification Entity & Migration

The Notification entity lives in HCM.Domain and is a simple inbox record scoped to a user:

Notification entity definition 
public class Notification
{
    public long Id { get; set; }
    public Guid UserId { get; set; }       // recipient
    public string Type { get; set; }         // CaseAssigned | TaskAssigned | TaskOverdue | CaseEscalated
    public string Title { get; set; }
    public string Message { get; set; }
    public string? EntityType { get; set; }   // "Case" or "Task" — drives deep-link
    public string? EntityId { get; set; }     // CaseNumber or Task GUID
    public bool IsRead { get; set; }
    public DateTime CreatedAt { get; set; }
    public DateTime? ReadAt { get; set; }
}

The EF configuration adds a composite index on (UserId, IsRead, CreatedAt) — the exact query shape used by both the bell badge query (WHERE UserId = X AND IsRead = false) and the list query (ORDER BY CreatedAt DESC TAKE 20). This makes both queries covered by a single index.

No FK from Notification → User — same design choice as AuditLog. Notifications must survive user deletion (deactivation) so the coordinator's history is preserved for compliance review. UserId is stored as a raw Guid, not a navigation property.

Notification Trigger Points

Notifications are created at the point of the business event — inside the DataHandler that owns that event — not in a generic event bus. This keeps the causality obvious and avoids out-of-process messaging infrastructure.

EventTypeWhere triggeredRecipient
Case created with an assigned coordinator CaseAssigned CaseDataHandler.CreateCaseAsync Assigned coordinator (if ≠ creator)
Case status changed to "Escalated" CaseEscalated CaseDataHandler.ChangeCaseStatusAsync Assigned coordinator (if ≠ changer)
Task created with an assignee TaskAssigned TaskDataHandler.CreateTaskAsync Assigned user (if ≠ creator)
Task reassigned to a different user TaskAssigned TaskDataHandler.UpdateTaskAsync New assignee
Task is past due date and still open TaskOverdue NotificationOverdueService (daily) Assigned user
Real-world analogy — No self-notifications: When a manager assigns a task to themselves, they don't need a notification — they already know. All four trigger points check that the recipient is different from the actor before creating a notification, preventing noisy self-spam.

Notification Data Handler

INotificationDataHandler is injected into both CaseDataHandler and TaskDataHandler as a scoped dependency. The interface is intentionally minimal:

INotificationDataHandler interface 
public interface INotificationDataHandler
{
    // Write path — called from other DataHandlers and BackgroundService
    Task CreateAsync(Guid userId, string type, string title, string message,
        string? entityType = null, string? entityId = null, CancellationToken ct = default);

    // Read path — called from NotificationsController
    Task<NotificationListDto> GetMyNotificationsAsync(Guid userId, int limit = 20, CancellationToken ct = default);
    Task<UnreadCountDto> GetUnreadCountAsync(Guid userId, CancellationToken ct = default);
    Task MarkReadAsync(Guid userId, long notificationId, CancellationToken ct = default);
    Task MarkAllReadAsync(Guid userId, CancellationToken ct = default);
}

The implementation registers as scoped in DependencyInjection.cs. Because it is scoped, it shares the same IApplicationDbContext instance as the calling handler within the same HTTP request — meaning the notification write happens in the same request lifecycle as the case/task save, but in a separate SaveChangesAsync call so the audit interceptor doesn't double-log it.

NotificationOverdueService (BackgroundService)

Some events are not triggered by an HTTP request — they are discovered by a scheduled scan. Task overdue notifications fall into this category: the system needs to check every day whether any assigned, incomplete tasks have passed their due date.

Real-world analogy — Night supervisor round: At the end of every shift, a supervisor walks through all open cases and flags anything that was due today but not completed. NotificationOverdueService does exactly this, automatically, every 24 hours.
How the overdue scan works
  1. Waits 2 minutes after startup (stagger to avoid hammering DB on deploy).
  2. Queries CaseTasks for rows where DueDate < today AND AssignedTo IS NOT NULL AND Status NOT IN (Done, Cancelled).
  3. For each matching task, checks whether a TaskOverdue notification for that exact EntityId was already created today — if so, skips it. This deduplication prevents the same user from receiving 30 "overdue" notifications for the same task over 30 days.
  4. Creates one TaskOverdue notification per task per day if not yet sent.
  5. Sleeps 24 hours and repeats.

The service uses IServiceProvider.CreateScope() to resolve scoped services (IApplicationDbContext, INotificationDataHandler) inside the singleton-lifetime hosted service — the standard .NET pattern for scoped-in-singleton access.

Notifications API Endpoints

All endpoints are under /api/notifications, require JWT auth, and operate on the current user only — no admin can read another user's notifications through this controller.

GET/api/notifications — latest 20 notifications, sorted newest-first; includes unreadCount
GET/api/notifications/unread-count — badge-only endpoint; returns { count: N }
POST/api/notifications/{id}/read — marks single notification as read; sets ReadAt
POST/api/notifications/read-all — bulk-marks all unread as read
Separate unread-count endpoint: The bell polls /unread-count every 60 seconds, not /notifications (which returns the full list). This keeps the polling payload tiny — just {"count":3} — and avoids the cost of fetching 20 rows and serializing them every minute while the user is just browsing other pages.

The Existing Audit Trail

HCMS has captured audit data since Phase 1. The AuditInterceptor in ApplicationDbContext.SaveChangesAsync intercepts EF ChangeTracker entries for tracked entity types (Patient, Case, CaseNote, User) and writes AuditLog rows after every save.

Each row contains:

  • EntityType — e.g. Patient, Case
  • EntityId — business key (MRN, CaseNumber) or GUID
  • Action — Created, Updated, Deleted, or custom strings like FhirExport
  • OldValues / NewValues — JSON snapshot of changed properties (only modified fields, not the whole row)
  • ChangedBy — User ID from the JWT claim (no FK — survives user deletion)
  • ChangedAt — UTC timestamp

Phase 7 adds no new writes to this table — it only adds the query layer that makes the data usable.

Audit Data Handler

AuditDataHandler builds a filtered, paginated EF query and enriches ChangedBy (a raw user ID string) with the corresponding username in a single batch lookup:

Username enrichment pattern 
// Collect all user IDs found in this page of results
var userIds = logs
    .Where(l => l.ChangedBy != null && Guid.TryParse(l.ChangedBy, out _))
    .Select(l => Guid.Parse(l.ChangedBy!))
    .Distinct().ToHashSet();

// One round-trip to get all usernames for this page
var userNames = userIds.Count > 0
    ? await _db.Users.AsNoTracking()
        .Where(u => userIds.Contains(u.Id))
        .ToDictionaryAsync(u => u.Id.ToString(), u => u.Username, ct)
    : [];

This avoids N+1 queries (one per log row) while keeping the audit table decoupled from the Users table (no FK). The dictionary lookup is O(1) per row after the single batch query.

Audit API Endpoint

A single endpoint, restricted to the Admin role, supports all query combinations:

GET/api/audit?entityType=Patient&action=Updated&changedBy=admin&from=2026-07-01&to=2026-07-04&page=1&pageSize=20

All parameters are optional. Unsupported combination of filters simply narrows the result set. Non-admin requests receive 403 Forbidden before the handler is ever called, because the controller is decorated with [Authorize(Roles = "Admin")].

Angular — Notification Bell

NotificationBellComponent is a standalone Angular component that renders in the top bar of AppShellComponent. It uses Angular Material's mat-menu as the notification dropdown — no custom overlay needed.

Component responsibilities
  • Badge: Subscribes to NotificationService.unreadCount (a BehaviorSubject<number>); passes the count to matBadge. The icon switches between notifications_none (no unread) and notifications (has unread) dynamically.
  • Dropdown open: Fires onMenuOpen() which calls GET /api/notifications and populates the list. The full list is fetched on demand (menu open), not on every poll — polls only check the count.
  • Mark read: Clicking a notification sends POST /api/notifications/{id}/read and decrements the badge locally for instant feedback. No round-trip needed to update the badge.
  • Mark all read: Calls POST /api/notifications/read-all and sets all items to read + clears badge in one shot.
  • Unread dot: A small blue dot appears on the right of each unread notification for visual distinction independent of the badge count.
Real-world analogy — Email preview pane: You don't download all your emails every minute — your inbox just shows an unread count badge. You only load the content when you open the pane. The bell works the same way: poll count cheaply, fetch details only when the user actually clicks.

Polling Strategy

NotificationService.startPolling() is called once in AppShellComponent.ngOnInit() — when the shell mounts after login. It uses RxJS interval(60_000).pipe(startWith(0)) to fire immediately on start and then every 60 seconds.

NotificationService polling implementation 
startPolling(): void {
  this.stopPolling();
  this.pollSub = interval(60_000)
    .pipe(
      startWith(0),
      switchMap(() => this.http.get<UnreadCountDto>(`${this.base}/unread-count`))
    )
    .subscribe({
      next: res => this.unreadCount$.next(res.count),
      error: () => {}   // silently ignore network errors during poll
    });
}

switchMap ensures that if the HTTP call takes longer than 60 seconds (network stall), the previous in-flight request is cancelled before the next interval fires — no concurrent polls.

Phase 8 upgrade path: Polling works well for the portfolio. In production, this should be replaced with SignalR — a WebSocket connection the server pushes to instantly when a new notification is created, eliminating the up-to-60-second delay and unnecessary HTTP round-trips.

Angular — Audit Log Component

AuditLogComponent is an Admin-only page accessible at /admin/audit. It presents the audit data as a filterable, paginated Material table with expandable rows for the JSON diff.

Features of AuditLogComponent
  • Filter panel: Entity Type dropdown (Patient, Case, CaseNote, User, Appointment, Task, Document), Action dropdown (Created, Updated, Deleted, FhirExport, FhirBundleImport), free-text "Changed By" username search, From/To date range pickers.
  • Table columns: Time (yyyy-MM-dd HH:mm), Entity, Entity ID (monospace), Action (color-coded badge), User.
  • Color-coded action badges: Created = green, Updated = blue, Deleted = red, FhirExport = purple, FhirBundleImport = orange — instantly readable at a glance.
  • Expandable JSON diff: Rows with OldValues or NewValues show an expand arrow. Clicking expands an inline panel with "Before" (amber background, amber left border) and "After" (green background, green left border) pre-formatted JSON. Uses JSON.parse → JSON.stringify(…, null, 2) for pretty-printing.
  • Pagination: Material paginator, page sizes 10/20/50/100; server-side, not client-side — only the current page is fetched.
  • Progress bar: mat-progress-bar at the top of the table card shows indeterminate loading during each query.

Admin Module Routing

Previously /admin pointed directly to a single AdminComponent stub. Phase 7 converts it to a lazy-loaded route subtree using ADMIN_ROUTES:

admin.routes.ts 
export const ADMIN_ROUTES: Routes = [
  { path: '', loadComponent: () => import('./admin.component') },
  { path: 'audit', loadComponent: () => import('./audit-log/audit-log.component') }
];

The AdminComponent landing page now shows a card grid of admin tools. Clicking "Audit Log" navigates to /admin/audit. Additional admin features (user management, system config) can be added as new routes here without touching app.routes.ts.

Key Decisions & Trade-offs

Why polling instead of WebSockets / SignalR?

SignalR (WebSockets) would give instant notifications — the server pushes to the client the moment a case is assigned. Polling with 60-second intervals means a user can wait up to a minute to see a new notification.

Decision: polling for now. SignalR requires server-side hub configuration, Angular client setup, and connection lifecycle management — meaningful added complexity for a portfolio project. Polling at 60s is well within acceptable UX for case management. The NotificationService.startPolling() method is the only call site, so swapping in a SignalR subscription later is a localized change.

The separate /unread-count endpoint (vs. polling the full list) keeps each poll cheap — a single integer in the response body.

Why no push subscription from TaskDataHandler → immediate bell update?

When the same user assigns a task to someone else, the assigner's browser doesn't need to update — only the recipient's. The recipient may be on a different browser session entirely. Server-side push (SignalR) is the correct solution for immediate delivery across sessions. Until SignalR is added, the 60-second poll is the mechanism that eventually delivers the new count to the recipient's bell.

Why long id (auto-increment) for Notifications instead of GUID?

The notification table will grow quickly — potentially thousands of rows per user over time. Long integers are:

  • Smaller on disk (8 bytes vs 16)
  • Cheaper to index
  • Naturally ordered by insertion time without a secondary sort column

Notifications are never exposed as a public URL (no IDOR risk from sequential IDs) — the controller scopes all queries to the authenticated user's ID. GUIDs would add cost with no benefit here.

Why no hard delete on notifications?

The current implementation does not expose a "delete notification" endpoint. The bell shows the latest 20; older notifications are still in the DB. This keeps the history available for support/debugging. A CleanupOldNotificationsService (e.g., purge records older than 90 days) would be a future housekeeping addition — safe to add without any API changes.

Why does AuditDataHandler re-join Users for usernames?

AuditLog.ChangedBy stores a raw User ID string, not a navigation property, because audit rows must survive user deletion. This means the username lookup requires a join at query time — but only for the current page (typically 20 rows). The handler collects the distinct User IDs in the page result, does a single WHERE Id IN (...) query, and builds a dictionary. Total round-trips: 2 (one for audit rows, one for usernames). This is O(1) extra queries regardless of page size.

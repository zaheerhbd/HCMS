What Was Built

Phase 3 adds two major capabilities to Case Detail:

  1. Document Management — upload PDF/DOCX/PNG/JPG files to Azure Blob Storage. Files are stored in a private container; SQL stores only metadata. Download links are time-limited SAS URLs (max 1 hour) generated on demand. Soft-delete is supported.
  2. Task Management — create and track tasks within a case. Tasks are assigned to care team members, have due dates with overdue detection, and move through a validated status lifecycle.

Both features are embedded in the Case Detail tab group as child components — CaseDocumentsComponent (Documents tab) and CaseTasksComponent (Tasks tab) — receiving the case number as an @Input().

Blob Storage Design

The core design decision is never store a blob URL in the database. Here's why that matters:

Analogy — SAS URL vs. permanent URL: Think of a document in a locked filing cabinet. A permanent public URL is like leaving the cabinet unlocked forever — anyone who finds the URL can access the file. A SAS URL is like a time-locked combination that expires: you get a unique code, use it within 1 hour, then it's worthless even if someone intercepts it.
SQL stores
BlobName (GUID), FileName, ContentType, FileSize, Category, IsDeleted
Blob stores
Raw file bytes at case-documents/{blobName} — private container, no public access
API generates
SAS URL on-demand: GET /api/documents/{id}/download-url → 1-hour signed URL, never logged
Why not store the blob URL in the database?

A blob URL is either public (accessible to anyone forever) or a SAS URL that embeds credentials and an expiry. Storing a SAS URL in the DB would mean every DB read leaks a short-lived credential. Storing a public URL violates HIPAA — medical documents must not be publicly accessible.

The clean approach: store only the logical blob name (a GUID). When a user requests a download, the server generates a fresh SAS URL, returns it to the client, and the client opens it in a new tab. The URL is never persisted anywhere.

Azure Blob Storage authentication flow

The IBlobStorageService is an abstraction in the Application layer. The Infrastructure implementation uses BlobServiceClient from the Azure Storage SDK, authenticated via DefaultAzureCredential. In production (Azure App Service), this resolves to Managed Identity — no credentials in code. Locally, it falls back to Azurite (the local blob emulator) configured in appsettings.Development.json.

Local dev requirement: Azurite must be running before the API starts. Run: azurite --silent --location .azurite --debug .azurite/debug.log

DocumentsController — API Endpoints

MethodRouteRoleDescription
POST/api/cases/{caseNumber}/documents/uploadCareCoordinator+Multipart upload; validates MIME type + size; uploads to Blob; saves metadata
GET/api/cases/{caseNumber}/documentsAllList documents for a case (excludes soft-deleted)
GET/api/cases/{caseNumber}/documents/{id}/download-urlAllGenerate 1-hour SAS URL; log download to AuditLogs
DELETE/api/cases/{caseNumber}/documents/{id}Supervisor+Soft-delete: sets IsDeleted = true; blob remains in storage

Validation Rules

  • Allowed MIME types: application/pdf, image/png, image/jpeg, application/vnd.openxmlformats-officedocument.wordprocessingml.document
  • Max file size: 20 MB (validated in DataHandler, not just Kestrel config)
  • MIME type is read from the uploaded bytes (via ContentType header), not just the file extension

Clean Architecture — Phase 3 Layer Map

Phase 3 introduces the IBlobStorageService abstraction. This is a good illustration of why Clean Architecture separates the Application and Infrastructure layers.

Domain
Document, CaseTask — pure entities, no dependencies
Application
IDocumentDataHandler, ITaskDataHandler, IBlobStorageService — interfaces only; no Azure SDK imports
Infrastructure
DocumentDataHandler (EF Core), TaskDataHandler (EF Core), AzureBlobStorageService (Azure SDK) — all implement Application interfaces
API
DocumentsController, TasksController — inject IDocumentDataHandler, ITaskDataHandler only; never reference Infrastructure directly
Analogy: The Application layer defines what it needs from storage (IBlobStorageService.UploadAsync()). The Infrastructure layer decides how — today it's Azure Blob Storage; tomorrow it could be S3 or a local filesystem. The API and Application layers never need to change when the storage provider changes.

Key Decisions & Trade-offs

DecisionChosenRejectedReason
File storage Azure Blob Storage (private container) Store files in SQL as varbinary SQL is optimised for structured data, not binary blobs. Blob Storage is cheaper, faster for large files, and supports CDN/streaming.
Download URL SAS URL generated on demand (1h expiry) Permanent public URL or server-proxied download Public URLs violate HIPAA. Server-proxied streaming wastes bandwidth. SAS URLs offload delivery to Azure CDN while keeping access controlled.
Blob deletion Soft-delete metadata; defer physical blob deletion Immediately delete blob on document delete Soft-delete preserves audit integrity. Physical deletion is a background job (Phase 8) — Azure doesn't charge much for cold storage in the meantime.
Task location Tasks embedded in Case Detail (CaseTasksComponent) Standalone Tasks module with its own route A care coordinator's primary workflow is case-centric. Embedding tasks in the case tab keeps the workflow cohesive. A MyTasksComponent (cross-case view) is still planned but deferred.
MIME validation Validate ContentType header + extension whitelist Extension-only check File extensions are trivially spoofed. ContentType is harder to fake but still not the gold standard — a full magic-bytes check would be ideal but is deferred as a stretch goal.

Security Notes

  • Blob container is private — no public access; all requests go through the API or a SAS token
  • SAS URLs are never logged to Application Insights (CLAUDE.md hard rule FR-25)
  • SAS URLs expire in 1 hour maximum — intercepted tokens have a short window
  • Every download is written to AuditLogs for HIPAA traceability
  • MIME type whitelist — only PDF, PNG, JPEG, DOCX accepted; anything else returns 400
  • Max 20 MB enforced in the DataHandler (not just Kestrel maxRequestBodySize)
  • Soft-delete only — documents are never physically removed until a scheduled cleanup job runs
  • Task endpoints use role-based auth — assignees can update status; only CareCoordinator+ can create or delete

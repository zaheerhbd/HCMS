What Was Built

Phase 5 adds a complete FHIR R4 API facade to HCMS. The existing internal domain model (patients, cases, appointments, tasks, documents) is translated into standard FHIR resources and served at the /fhir/R4/ base path — separate from the internal /api/ routes. The facade does not replace internal APIs; it is a standards-compliant read/export/import layer on top of the existing domain.

Four capabilities were delivered:

  1. Read & Search — query any FHIR resource type (Patient, Encounter, Appointment, Task, DocumentReference) with typed FHIR JSON responses.
  2. CapabilityStatement — the GET /fhir/R4/metadata endpoint self-describes the server's supported resources and search parameters, enabling tool discovery.
  3. $everything Bundle — a single call to GET /fhir/R4/Patient/{mrn}/$everything returns a FHIR collection Bundle containing the patient and all related resources. Useful for transferring a complete patient record to another system.
  4. Patient Import — POST /fhir/R4/Patient accepts a FHIR Patient JSON payload, validates it with the Firely SDK, maps it to the HCMS domain model, creates the patient, and writes an audit record to FhirImportLogs.

Why FHIR?

Real-world analogy: Think of healthcare IT systems as different countries, each speaking its own language: Epic speaks Epic, Cerner speaks Cerner, and every hospital's EHR is an island. FHIR (Fast Healthcare Interoperability Resources) is like adopting English as a common second language — every system still has its own internal dialect, but they can all communicate outward using FHIR JSON over standard HTTP. Once you speak FHIR, any compliant tool (Apple Health, Google Health, CMS portals, payer systems) can read your data without custom integration.

FHIR R4 is the current production standard mandated by ONC/CMS regulations for healthcare data exchange in the United States. Adding a FHIR facade to HCMS demonstrates that the system is:

  • Interoperable — can participate in a broader healthcare ecosystem without bespoke ETL pipelines.
  • Regulatory-aware — the 21st Century Cures Act requires certified EHR systems to provide FHIR API access to patient data.
  • Portfolio-ready — FHIR knowledge is a concrete differentiator for roles in digital health, healthtech, and clinical informatics engineering.

Architecture Overview

The FHIR facade is layered inside the existing Clean Architecture without violating its rules. FHIR-specific concerns live in the Application and Infrastructure layers; the API layer stays thin.

Design principle: The FHIR facade shares the same ApplicationDbContext, entities, and existing DataHandlers as the internal API. There is no separate FHIR database, no duplication of patient data. The mapping layer is purely a translation concern — domain objects go in, FHIR JSON comes out.

Firely .NET SDK

Real-world analogy: Serializing FHIR resources by hand is like writing your own JSON serializer — technically possible, but you'd be re-implementing a standard that already has a battle-tested library. The Firely SDK is the official .NET FHIR library from HL7 Netherlands. It handles: model classes for every FHIR resource type, strict serialization/deserialization with validation, and the complex nested type system FHIR uses (e.g., HumanName, ContactPoint, CodeableConcept). Using it means our FHIR output is specification-compliant by construction.

The Firely .NET SDK v6.2.1 (Hl7.Fhir.R4) is added to HCM.Infrastructure. Key API choices for this version:

SDK Investigation Approach

When the Firely v6 API surface differed from online documentation (which often targets v4/v5), we inspected the NuGet package's XML documentation files directly in the package cache:

%USERPROFILE%\.nuget\packages\hl7.fhir.r4\6.2.1\lib\net8.0\Hl7.Fhir.R4.xml
%USERPROFILE%\.nuget\packages\hl7.fhir.base\6.2.1\lib\net8.0\Hl7.Fhir.Base.xml

Using Select-String on the XML docs to find correct class names, method signatures, and enum locations. This approach avoids relying on outdated blog posts and gives ground truth from the installed version.

DataHandler Pattern Applied to FHIR

FHIR endpoints follow the same project-wide DataHandler architecture as all other features. The controller is thin; all query logic, validation, and mapping delegation lives in FhirDataHandler.

// Controller — just routing + return
[HttpGet("Patient/{mrn}/$everything")]
public async Task<IActionResult> GetEverything(string mrn)
{
    var json = await _fhirHandler.GetEverythingAsync(mrn);
    return Content(json, "application/fhir+json");
}

// DataHandler — business logic
public async Task<string> GetEverythingAsync(string mrn)
{
    var patient = await _db.Patients.Where(p => p.MRN == mrn && p.IsActive).FirstOrDefaultAsync()
        ?? throw new NotFoundException("Patient", mrn);
    // ... load related resources, write AuditLog, call FhirMappingService
    return _mapper.MapEverythingBundle(patient, cases, appointments, tasks, docs);
}

The controller returns Content(json, "application/fhir+json") instead of Ok(object) to prevent ASP.NET's JSON serializer from re-serializing the already-serialized Firely output (which would double-encode the string and produce invalid JSON).

Error Handling — OperationOutcome vs ProblemDetails

Real-world analogy: The internal /api/ routes use RFC 7807 ProblemDetails — the REST world's standard error format. But FHIR routes have their own error standard: OperationOutcome. It's like how a US customs form and a UK customs form both capture the same information but in different layouts. A FHIR client expects OperationOutcome; giving it ProblemDetails would break interoperability.

The existing ExceptionHandlerMiddleware was extended to detect the request path:

  • Requests to /fhir/* → return FHIR OperationOutcome resource as application/fhir+json
  • All other requests → return RFC 7807 ProblemDetails as application/problem+json
// In ExceptionHandlerMiddleware
if (context.Request.Path.StartsWithSegments("/fhir"))
{
    context.Response.ContentType = "application/fhir+json";
    // Return OperationOutcome JSON
}
else
{
    context.Response.ContentType = "application/problem+json";
    // Return ProblemDetails JSON
}

FHIR API Endpoints

All endpoints are at base path /fhir/R4 and produce/consume application/fhir+json. All except GET /metadata require a valid Bearer JWT.

Metadata

GET/fhir/R4/metadata

Returns the server's CapabilityStatement. Anonymous — no authentication required. Declares all supported resource types, operations, and search parameters.

Patient

GET/fhir/R4/Patient

Search patients. Query params: _id (GUID), name (partial match), birthdate (exact), identifier (MRN). Returns FHIR Bundle of type searchset.

GET/fhir/R4/Patient/{mrn}

Read single Patient resource by MRN. Returns 404 OperationOutcome if not found.

GET/fhir/R4/Patient/{mrn}/$everything

Returns a FHIR Bundle of type collection containing the Patient and all related Encounters, Appointments, Tasks, and DocumentReferences. Writes an AuditLog entry with action FhirExport.

POST/fhir/R4/Patient

Import a patient from a FHIR Patient JSON payload. Validates with Firely SDK, maps to internal domain, creates patient (with MRN generation), logs to FhirImportLogs. Returns the generated MRN and success status.

Encounter

GET/fhir/R4/Encounter

Search Encounters. Query params: patient (MRN), status. Returns FHIR Bundle searchset.

GET/fhir/R4/Encounter/{caseNumber}

Read single Encounter by case number.

Other Resources

GET/fhir/R4/Appointment/{id}
GET/fhir/R4/Task/{id}
GET/fhir/R4/DocumentReference/{id}

Read single resource by internal GUID for Appointment, Task, and DocumentReference.

CapabilityStatement

Real-world analogy: A CapabilityStatement is the FHIR equivalent of a restaurant menu — before a customer (FHIR client) even orders, they can see what's available, what search options exist, and what the kitchen (server) supports. Tools like the SMART on FHIR app launcher and FHIR validators hit /metadata first to understand what they can ask for.

The CapabilityStatement is built programmatically by FhirMappingService.GetCapabilityStatement() using the Firely model classes. It declares:

  • Server kind: instance
  • FHIR version: R4
  • Supported resource types: Patient, Encounter, Appointment, Task, DocumentReference
  • Supported interactions per resource: read, search-type
  • Search parameters per resource type (e.g., _id, name, birthdate for Patient)
  • Supported operation: $everything on Patient

$everything Bundle Flow

Patient Import Flow

The import flow allows an external FHIR system (another EHR, a patient portal, or an integration engine) to push a patient record into HCMS by sending a standard FHIR Patient JSON payload.

  1. User pastes or uploads a FHIR Patient JSON into FhirImportComponent.
  2. Angular's FhirService.importPatient(fhirJson) posts the raw JSON to POST /fhir/R4/Patient.
  3. The controller reads the raw request body as a string (no model binding — avoids ASP.NET's serializer interfering with FHIR JSON).
  4. FhirDataHandler.ImportPatientAsync():
    • Calls FhirMappingService.ParsePatientFromFhir(fhirJson) — Firely SDK deserializes and validates the payload.
    • Maps FHIR fields to a CreatePatientDto.
    • Calls the existing IPatientDataHandler.CreatePatientAsync() to create the patient with MRN generation.
    • Writes a FhirImportLog record with: ResourceType, SourceSystem, FhirResourceId, InternalId (MRN), Status (Success/Failed), ErrorMessage (if any), ImportedBy, ImportedAt, RawPayload.
  5. Returns FhirImportResultDto with generated MRN and success flag.
  6. Angular shows a success snackbar with a "View" action that navigates to the new patient's detail page.
Audit trail: Every import writes to FhirImportLogs with the full raw payload. This table has no FK to Users (survives user deletion), no DELETE or UPDATE endpoint, and two indexed query paths: by ImportedAt and by (ResourceType, Status). This satisfies HIPAA requirements for import audit trails.

Angular FHIR Module

The FHIR feature is a lazy-loaded standalone route group at /fhir. It adds two components and a service, and extends two existing components (PatientDetail, PatientList).

// app.routes.ts — lazy-loaded FHIR routes
{
  path: 'fhir',
  loadChildren: () => import('./features/fhir/fhir.routes').then(m => m.FHIR_ROUTES)
}

// fhir.routes.ts
export const FHIR_ROUTES: Routes = [
  { path: 'explorer', component: FhirExplorerComponent },
  { path: 'import',   component: FhirImportComponent   },
];

FhirService constructs the FHIR base URL by stripping /api from the configured API URL and appending /fhir/R4. Methods return typed observables:

  • getMetadata() → Observable<any>
  • getResource(type, id) → Observable<any>
  • searchPatients(params) → Observable<any>
  • getEverything(mrn) → Observable<Blob> (for file download)
  • importPatient(fhirJson) → Observable<FhirImportResult>

FHIR Explorer Component

FhirExplorerComponent is a developer/admin tool for interactively querying the FHIR API and inspecting raw responses. It is accessible to users with Admin or Supervisor roles via the sidebar "FHIR" navigation item.

  • Resource type dropdown: Patient, Encounter, Appointment, Task, DocumentReference, metadata
  • ID input field (hidden for metadata, optional for search)
  • Execute button sends the request via FhirService
  • Response displayed using ngx-json-viewer — a collapsible JSON tree that makes deeply nested FHIR resources navigable
  • Error display shows the raw OperationOutcome issue[0].diagnostics text
Real-world analogy: The FHIR Explorer is like Postman, but built into the app. Rather than making a recruiter switch tools to inspect FHIR output, they can see live FHIR responses from the same browser tab they're already in.

FHIR Import Component

FhirImportComponent supports three input methods:

  1. Paste JSON — a resizable textarea for pasting a FHIR Patient payload directly.
  2. File Upload — a file input that reads a .json file and populates the textarea.
  3. Load Sample — pre-fills the textarea with a realistic FHIR Patient JSON template so users can test the flow without needing an external payload.

On submission, error handling parses the OperationOutcome response and displays individual issue diagnostics as a list, making validation failures actionable (e.g., "Patient.name is required" rather than a generic 400 error).

Patient Export Button

The "Export as FHIR Bundle" stroked button was added to the header-actions section of PatientDetailComponent. It:

  1. Calls FhirService.getEverything(mrn) with responseType: 'blob'.
  2. Creates a temporary object URL from the Blob.
  3. Programmatically clicks a hidden <a> element to trigger the browser's file download with filename patient-{mrn}-fhir-bundle.json.
  4. Revokes the object URL to free memory.

The exportingFhir boolean flag controls a loading spinner on the button during the download.

Key Decisions & Trade-offs

Decision: FHIR Facade, Not Native FHIR Storage

Choice: Translate existing domain entities to FHIR on-the-fly rather than storing data natively in FHIR format.

Why: Native FHIR storage would require rebuilding the entire data model around FHIR resource types. For a portfolio project, the translation approach demonstrates FHIR knowledge while keeping the domain model clean and SQL-friendly for operational queries (search, pagination, filtering).

Trade-off: Translation adds a thin latency layer. In a production system handling high FHIR query volumes, a dedicated FHIR server (HAPI FHIR, Azure Health Data Services) would be more appropriate. The facade approach is common in real-world integrations as well — many organizations run an internal operational DB and expose FHIR externally.

Decision: Firely SDK vs Hand-Rolling FHIR JSON

Choice: Use the official Firely .NET SDK (Hl7.Fhir.R4) for serialization, deserialization, and model construction.

Why: FHIR has hundreds of resource types, each with complex nested types (HumanName, CodeableConcept, Reference, Period, etc.). Hand-rolling the JSON for even five resource types would be brittle and non-compliant. The Firely SDK produces specification-compliant FHIR JSON guaranteed.

Trade-off: The SDK adds ~10 MB to the build. In v6.2.1 the API changed significantly from v4/v5 (see SDK Fixes section), requiring investigation of the package's XML docs.

Decision: Separate /fhir/R4/ Path from /api/

Choice: FHIR endpoints at /fhir/R4/; internal API at /api/. Two completely separate route trees.

Why: FHIR has its own conventions: application/fhir+json content type, OperationOutcome errors, resource-centric URL patterns (/Patient not /patients). Mixing FHIR and REST conventions in the same path would violate both standards.

Trade-off: Two sets of auth checks and middleware to maintain. The middleware FHIR path detection (Path.StartsWithSegments("/fhir")) is simple and reliable.

Decision: Return Content(json) Not Ok(object)

Choice: All FhirController actions return Content(json, "application/fhir+json").

Why: If we returned Ok(firehJsonString), ASP.NET's System.Text.Json serializer would see a string and serialize it as a JSON string literal (with escape characters), breaking the FHIR JSON structure. Returning Content() bypasses ASP.NET's serializer and writes the raw string directly to the response body.

Decision: FhirImportLogs Has No FK to Users

Choice: FhirImportLog.ImportedBy is a plain string (username), not a foreign key to Users.

Why: Consistent with the AuditLogs table rule in CLAUDE.md: audit records must survive user deletion. If we FK'd to Users and an admin deleted a user account, the import history would cascade-delete or orphan. Storing the username string preserves the audit trail regardless of user account lifecycle.
